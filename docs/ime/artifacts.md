# 焼き付け成果物 — 収穫と焼き付けを分け、鮮度と中身をゲートで守る

> **問ひ**（issue #4）: 変換・辞書・RAG を検証できる環境が無い。
> だが CI はすでに ubuntu 主体で組まれてゐて、新しく Linux CI を導入する余地は無い。
> **変換 / RAG を既存の ubuntu 段へ載せられる形に切り出せるか。**
>
> **答**: 切り出せる。鍵は「**通信して非決定的な仕事**」と「**通信せず決定的な仕事**」を
> 分けること、そして後者だけを CI に載せることである。前者の結果は
> **成果物としてコミットし、CI では再計算しない**。

## 1. 収穫と焼き付け

このリポジトリは既にこの分離を持つてゐた。`core-ci.yml` の注記がそれである:

> bigram の収穫（`gen_yatate_ngram.py`）は青空文庫へ通信するので CI では回さない。
> 表を起こす側（`gen_bigram_tables.py`）は通信しないのでここで回せる。

issue #4 はこの形を辞書と RAG へ広げるだけの話に落ちる。

| | 収穫（harvest） | 焼き付け（bake） |
|---|---|---|
| 通信 | **する**（青空文庫・埋め込みモデル） | しない |
| 決まり方 | 非決定的（カタログが時とともに変はる） | **決定的**（同じ入力 → 同じ出力） |
| いつ回すか | オフラインで一回。人が回す | 毎回。**CI が回す** |
| 費用 | 時間と帯域（と、埋め込みならモデル） | $0 |
| 出口 | `core/data/*` へコミット | 生成物へ書き出し、`git diff --exit-code` |

現在ある対:

| 収穫 | 焼き付け | 成果物 |
|---|---|---|
| `scripts/gen_yatate_ngram.py` | `scripts/gen_bigram_tables.py` | `core/data/kana_bigram.txt` → Swift・Rust の bigram 表 |
| `scripts/harvest_jisho.py` | `scripts/gen_jisho_tables.py` | `core/data/jisho.tsv` → `core/src/generated/jisho_table.rs` |
| （別リポ・未着手） | （未着手） | 埋め込み・索引 — §4 |

## 2. 境界 — どこまでを核へ、どこからを別リポの契約テストへ

issue #4 が「先に決める必要がある」とした点である。判定は `core/src/lib.rs` が
核に課してゐる三条件（**決定的・依存ゼロ・UI を知らない**）で機械的に決まる。

| 仕事 | どこ | 理由 |
|---|---|---|
| 旧字確定・仮名の正規化 | **核**（済） | 純関数 |
| 原器・入力の状態機械 | **核**（済） | 純関数 |
| **辞書引き**（読み → 表記・費用） | **核**（本 issue で実装） | 表を焼き付ければ決定的 |
| **格子探索・文節分割・費用計算** | **核**（本 issue で実装） | 整数演算のみ。浮動小数を使はない |
| **区切り修正**（繋げる・割る・読み列） | **核**（本 issue で実装） | `protocol.md` §1 が「端末側の半分」と呼ぶもの |
| **読みの被覆検査** | **核**（本 issue で実装） | 変換の中核の不変条件 |
| 量子化ベクトルの近傍探索 | **核**（未着手・§4） | 索引が焼き付けてあれば決定的 |
| 埋め込みの**計算** | 別リポ | モデル・資格情報・通信が要る |
| 索引の**構築** | 別リポ（＝収穫） | 同上 |
| 情調（共感覚）・色 | 別リポ | コーパス由来の非決定的な推定 |
| LLM の折り返しループ・文の生成 | 別リポ | 定義から非決定的 |
| `/convert` の JSON スキーマ | **両側**（契約テスト） | 契約は片側では守れない |

言ひ換へると、**「引く側」は核、「作る側」は別リポ**である。
索引は作るのに通信と模型が要るが、引くのは表を舐めるだけなので決定的になる。
この線を引いたことで、issue #4 が採らなかつた案 b（「変換の中身が検証されないまま残る」）を
避けつつ、案 c（「CI に通信とモデルが要り $0 で回らなくなる」）にも落ちない。

## 3. 成果物の形式 — テキストを第一とし、目録が全部を覆ふ

issue #4 の「バイナリだと差分が見えないので、鮮度ゲートをハッシュで見るか、
テキスト形式にするか」への答へは **両方**である。片方では足りない。

| | テキスト（TSV・行形式） | 目録（`core/data/MANIFEST.sha256`） |
|---|---|---|
| 何が見えるか | **何がどう変はつたか** | **変はつたかどうか**だけ |
| 効く相手 | 辞書・bigram | すべて（埋め込み・索引を含む） |
| 大きさの限界 | 数 MB まで | 無し |

規約:

1. **テキストで持てるものはテキストで持つ。** 辞書は人が眺めて直す成果物であり、
   「なぜ候補が変はつたか」が差分で読めることに価値がある。
2. **並びは焼き付けが正規化する。** `gen_jisho_tables.py` は `jisho.tsv` 自身を
   読み昇順・度数降順・表記昇順へ書き直す。手で足した行が順序を崩しても、
   鮮度ゲート（再生成 → `git diff --exit-code`）が拾ふ。
3. **すべての成果物を目録に載せる。** `core/data/` の下にあつて目録に無いファイルは
   `check_artifacts.py` が失敗にする。関門を持たない成果物を作らせない。
4. **目録が塞ぐ穴は「収穫の成果物そのもの」である。** 鮮度ゲートは「元を変へたのに
   写しが古い」を捕まへるが、元そのもの（`kana_bigram.txt`）は CI で再生成できない
   ——通信するからである。そこには今まで何の関門も無かつた。

## 4. 埋め込みと索引 — 置き場・大きさ・LFS

**関門は先に置いた。成果物はまだ無い**（コーパスと埋め込みモデルが別リポジトリに在るため）。
落ちてきたときの規約を先に決めておく。

### 置き場と形式

```
core/data/sakuin.bin      量子化した埋め込み（int8 ＋ 行ごとの scale）。目録が縛る
core/data/sakuin.meta     テキスト。模型名・次元・件数・量子化方式・収穫日。差分が読める
core/data/sakuin.tsv      チャンクの出典（作品名・著者・位置）。テキスト
```

**バイナリにする。** 埋め込みをテキストにすると 3〜4 倍に膨らむ上、
どうせ人には読めない（全行が変はる）ので、テキストにする益が無い。
代はりに `.meta` を隣へ置き、**人が読むべきことはそこへテキストで書く**。

### 大きさ

| 形 | 20,000 チャンク × 384 次元 |
|---|---|
| float32（生） | 約 30 MB |
| **int8 ＋ 行 scale**（採る） | **約 7.7 MB** |

上限を **1 ファイル 25 MB・`core/data/` 合計 50 MB** と定める。
超えるなら、まづ量子化・次元削減・チャンクの間引きで収める。

### Git LFS は採らない

1. 無料枠は**帯域**で切れる（月 1 GB）。CI の checkout ごとに消費するので、
   ランナーが増えるほど痛む。$0 で回すといふ本リポジトリの前提と噛み合はない。
2. 「clone すれば全部ある」といふ公開リポの性質が壊れる。
3. **CI は埋め込みを読まない**（ハッシュしか見ない）。読まないものの帯域だけ払ふのは筋が悪い。

上限に収まらないほど大きくなつたら、LFS ではなく
「リポジトリに入れるのは量子化した索引と目録だけ、生の float32 は別リポに残す」を採る。

## 5. 模型を差し替へたとき — 差分をどう見せるか

全ベクトルが変はるので `git diff` は無意味になる。issue #4 が挙げた通りである。
**見せるものを三つに分ける。**

| 見せるもの | どこに出るか |
|---|---|
| **何を変へたか** | `sakuin.meta` の一行差分（模型名・次元・量子化） |
| **本当に変はつたか** | 目録の一行差分（sha256） |
| **良くなつたか悪くなつたか** | **golden query セットの差分** |

三つ目が肝である。ベクトルの中身を見比べても人には何も分からないが、
「この問ひに対して出る答へがどう変はつたか」なら読める。
本 issue で辞書について既にこの形を入れてある——`core/vectors/bunsetsu.json` は
代表的な読みに対する分割・候補・費用を核が書き出したもので、
`core/tests/parity.rs` がそれを流す。辞書を一語足しただけで無関係な文の分割が変はれば、
**そのファイルの差分としてレビューに現れる**。埋め込みが入つたら
`core/vectors/kensaku.json` を同じ形で足す。

再焼き付けの手順:

```bash
# ① 収穫（通信あり・オフラインで一回）
python3 scripts/harvest_embeddings.py --model <新しい模型>   # 別リポ or 未着手
# ② 焼き付け（通信なし・決定的）
python3 scripts/gen_sakuin.py                                 # 未着手
# ③ 目録を書き直す
python3 scripts/check_artifacts.py --update
# ④ golden query を引き直し、差分をレビューに載せる
cargo run --manifest-path core/Cargo.toml --bin gen-vectors
```

## 6. いま張つてある関門

すべて **ubuntu（課金 1 倍）** で回る（`docs/ime/cross-platform.md` §7）。

| 関門 | 何を捕まへるか | どこ |
|---|---|---|
| `python3 ssot/test_kyuji.py` | 旧字表の SSOT | `core-ci.yml` |
| `cargo test --all-targets` | 核の単体試験 ＋ 黄金ベクトル | 同上 |
| `check_artifacts.py` | **収穫の成果物が黙つて書き換はること**・関門の無い成果物 | 同上 |
| 鮮度ゲート（再生成 → `git diff`） | 「元を変へたのに写しが古い」 | 同上 |
| `bunsetsu.json`（golden query） | **辞書・費用を触つたときの変換品質の回帰** | `core/tests/parity.rs` |
| `clippy` / `fmt` | 体裁 | `core-ci.yml` |

## 7. やり残し

- **埋め込みの成果物そのもの**。§4 の規約と関門は入つたが、コーパスと模型が別リポジトリに
  在るので実体はまだ無い。落ちてきた日に目録へ載せれば、その日から守られる。
- **`sakuin` の近傍探索を核へ**。索引が焼き付いてゐれば決定的なので核に置けるが、
  引く相手が無いうちに書いても「動くやうに見えて動かないコード」が残るだけである
  （`windows/` が M7-a で同じ判断をしてゐる）。
- **辞書の実収穫**。いま入つてゐる `jisho.tsv` は 232 語の**種**である。
  `harvest_jisho.py` を一度回せば青空文庫のルビから数千語に育つ
  （付属語はルビから取れないので、種の側が引き継がれる）。
- **費用の重み**。`NEW_BUNSETSU_AFTER_JIRITSU` などの値は素朴な手置きである。
  辞書が育つたら golden query セットを物差しに測り直す余地がある（そのときも整数のまま）。
